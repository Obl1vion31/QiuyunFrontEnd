# 已确认决定

本文件只记录已经确认、会影响后续工作的产品、结构和技术结论。

## 产品定位

- 当前产品暂称“前端团队管理系统”。
- 网站长期目标是承载前端业务工作、数据、规则、复盘和协作入口，不应停留在静态宣传页。
- 首页以部门工作流为主要叙事，呈现策划、内容、视觉、发布、用户触点和反馈回流如何组成完整流程；对外文案不强调个人或当前人员安排。
- 总枢纽首页是系统入口，不是整个系统，也不是实时业务驾驶舱。
- 前端负责从用户看见内容，到阅读、产生兴趣、形成咨询并完成有效交接的过程；最终销售成交仍属于销售侧边界。
- 原始业务数据不应主要存放在周报或月报中；报告是输出视图，不是事实来源。

## 当前页面边界

- 当前正式界面包含总枢纽首页、年度内容总周期规划和运营内容排期 MVP。
- 首页用于解释前端存在的意义、完整工作链路和后续系统入口。
- 首页首屏同时呈现工作台定位与前端使命：以 `FRONTEND CONTENT WORKSPACE` 说明平台属性，以 `WHY WE EXIST` 说明内容触达目标；不再设置独立的使命区块。
- 首页不展示实时数据、周报明细、月报明细、当前项目列表、完整业务排期或个人绩效薪资明细。
- 首页当前保留业务系统、组织与人员、绩效与报酬三个方向的入口概念。
- 业务系统入口连接 `/business/operations-schedule`；组织与人员、绩效与报酬继续保持占位或授权入口。
- 排期以“新做帖”和“改帖”区分内容生产动作：新做帖建立 V0，改帖从原版本派生 V1/V2 并保留版本链；“编辑排期”只更正资料、应发时间与用途，不代替改帖，也不承担实发登记。
- 创建改帖只填写一项“具体改动说明”，说明具体改动部分、改动原因与希望达到的效果；不再单独记录改动类型和修改目标。
- 帖子身份、内容版本和发布排期分别保存；历史排期不猜测关联，每条作为独立 V0。
- 学科与帖子分类是两个独立的固定字典，通过映射决定学科可用分类。TMUA 与 STEP 使用“出分合集”，面试课仍保留独立“喜报”；增加固定“临时帖”分类和“临时学科 / 临时帖”兜底组合，历史空分类归入临时帖；新建或编辑时必须选择有效分类，不强制绑定年度规划行。
- 年度细致规划行优先使用“学科 + 帖子分类”作为显示名称；帖集使用统一的 ` [帖集]` 后缀。机器关联始终以 `subject_id + category_id` 为准，不根据中文名称反查。
- 总周期规划位于具体内容排期上游，默认以一个自然年度页面同时展示总规划和各学科细致规划，不在当前阶段自动生成帖子、内容版本或排期。
- 年度规划以“学科分区 → 有序细致规划行 → 一个或多个时间块”组织。细致规划行复用现有学科与分类关系，以 `subject_id + category_id` 表达学科和帖子类别，不再填写或展示课程名称；数据库旧空列和历史快照字段只保留兼容。
- 总规划不作为可编辑规划行保存，而是从启用的细致规划自动汇总：全部启用时间块形成内容流动周期，块内付费区间形成付费推广周期；整行推广标记只保留兼容，不作为新汇总依据。旧总规划记录由受控迁移清理，不进入页面和计算；没有帖子来源的 G5 不建立细致规划或占位汇总。
- 时间块保存半月起止、可选阶段名称、自由备注和块内付费区间。同一行可以有多个不连续时间块但不能重叠；月中结束覆盖上半月，月中开始从下半月起算。页面不计算或显示数量公式，未确定内容可直接填写“待定”。班课全程推广、讲义与模考首月推广是配置策略，编辑器不据此限制用户调整。
- 年度规划的主要 HTTP/HTTPS 链接属于规划行，一行可以保存多个。所有有效修改生成包含规划行、时间块和链接的不可变版本快照，恢复历史时创建新版本，不覆盖旧历史。
- 年度规划新建为 V0，后续真实调整逐次追加版本，历史快照不可变；快照格式 v4 保存半月与付费区间，v2/v3 在读取和恢复时转换为新格式。历史初始化规则：新建规划行为 V0，首次实际修改后进入 V1。2026 年 7 月 28 日以前为搭建和录入产生的中间版本历史不作为业务变更历史保留，只保留每条规划的当前内容并归档为 V0；该规则不改变内容发布排期自身的新做帖 V0 / 改帖 V1+ 版本链。
- 细致规划的显示顺序跟随帖子分类字典；停用行默认隐藏且不参与汇总。SOP 在矩阵中只显示链接箭头，链接名称不作为主要业务信息。
- 规划行唯一约束为同一年、同一分区、同名规划项目唯一；同一分类可以服务多个不同用途的规划行。正常新建不强制数量、分类、时间块或手填变更说明。
- 年度复制仅写入空白目标年度，复制年度说明、全部细致规划、启停状态、时间块、备注、付费区间与行级链接；新行使用独立 ID 和 V0，不复制来源版本链，不覆盖目标配置。复制与常规年度写入共用事务锁。
- 排期支持新做帖、编辑排期、独立实发登记、从原版本发起改帖和受保护删除，不支持通用上传导入或导出。删除只用于清理没有改帖版本链、推广活动、非推广指标、复盘记录或用途变更记录的独立排期；删除时同步清理其唯一 V0 和帖子主体，存在任一下游数据时必须拒绝删除。
- 内容发布控制台已实现总周期规划、排期管理、日度推广复盘、非推广首轮/二轮复盘和周度业务复盘；月/年汇总、独立数据填报和报表中心仍只显示规划状态。
- 内容发布控制台的异步交互统一由共享壳层提供动作文字、忙碌状态和防重复触发；页面专项反馈可以补充，但不能让存在等待时间的操作处于无提示状态。
- 排期管理使用统一的按日期分组时间轴台账承载大数据量，并保留月历切换；推广中不再作为独立看板，而是同一数据集的筛选视角，并拆分显示测试中与放量中数量。
- 桌面端使用 `Sidebar + Toolbar + Inspector + Sheet` 结构：Inspector 查看当前帖子详情和版本链，Sheet 承载新做帖、编辑排期和创建改帖；移动端导航转为底部 Bar。
- “推广”只指花钱测试或放量的内容。排期使用独立的 `is_promoted` 布尔字段稳定标识是否属于推广帖，推广状态表达非推广、待推广、推广测试中、推广放量中、等待行动、推广周期已结束、测试淘汰和放量淘汰；结束、淘汰或等待期间仍保持 `is_promoted = true`。推广周期已结束表示内容未被淘汰而自然结束一轮推广，测试淘汰表示测试后停止投入，放量淘汰表示进入放量后停止投入，“推广中”只统计推广测试中和推广放量中。
- “等待行动”属于日度复盘的下一步决定，不是当天可自由切换的状态。测试或放量日选择等待后，下一自然日以消耗和四项人数全零进入待确认队列且不计入测试/放量天数；等待日仍需选择下一步并确认，测试等待可继续等待、测试继续、测试淘汰或测试转放量，放量等待可继续等待、放量继续、放量淘汰或自然结束。系统不根据零消耗自动推断等待。
- 应发与实发精确到分钟并按 `Asia/Shanghai` 解释；实发通过独立登记入口保存，完成情况不由用户选择，而是自动归一化为待发布、按时发布或延期发布。满应发 8 小时进入延期第 1 天，以后每满 24 小时新增一天；每一天必填责任方（自身／需求端）和文字原因，实发登记原子补齐欠填理由。历史原因逐日复制，空原因填“未知”，责任方标记历史未确认并保留历史补齐来源。
- employee 修改已有应发时间必须申请并经 admin 审批；批准前按原排期计时，批准后按新时间重新计时，旧逐日理由与欠填事项保留。admin 直接改期也填写理由，改期与审批均留存经验证的操作者和时间。团队共享延期、待补理由和审批队列；延期数量按排期记录计数，理由填完但未实发时仍显示延期。
- 新做帖、创建改帖和编辑排期允许项目文档链接为空；缺失文档在未实发阶段是正常的“待登记”状态。实发登记必须同时填写 HTTP/HTTPS 项目文档链接；数据库保留可空的 `project_doc_name` 兼容历史数据。
- 一次性历史数据导入必须使用默认只读预检、显式写入、事务保护和幂等键；完成后移除批次脚本，不在核心文档保留具体文件名、月份、条数或清理结果。当前不建设通用上传或自动同步。
- 内容发布控制台的 Phase 05 第一阶段只建设推广帖 Daily Promotion Review：每天填写消耗、平台/实际开口人数和平台/实际留资人数，只自动计算实际开口成本与实际留资成本；点击率保留为空并留待周复盘口径。最新生命周期按帖子使用独立的全宽卡片，固定以北京时间昨天为截止日，以自然日比例展示昨天有效的测试与放量阶段，并在条外显示完整日期区间；不随日度待填日期变化，不使用共享月份网格、垂直游标或逐日圆点。测试统一为黄色，放量统一为绿色。每日复盘只展示当前活动截至昨天尚未完成的日期，连续漏填全部列出但必须依次完成，已经填写的日度事实只在历史总览查看。历史总览默认 90 天，支持帖子与日两种粒度；帖子视角优先显示进行中活动并折叠已结束活动，日视角按日期汇总消耗、平台开口、实际开口和实际留资。非推广复盘、周月年复盘、独立数据填报和报表中心不进入该阶段的首轮实现。
- 已保存的推广日度事实允许登录账号更正消耗、四项人数和备注；下一步与生命周期更正仅管理员可执行；日期、帖子、活动和阶段快照保持系统只读。修改下一步且存在后续事实时，必须先展示影响数量并二次确认，再在事务中删除后续事实、重建阶段与活动状态，并同步排期推广状态；被删除日期重新进入连续待办队列。
- 推广帖填写实发日期后先进入“待开始推广”，不自动建立推广活动；日度待办可以把当天确认成“当日未推广”，只推进排期的确认日期游标，不生成空指标事实。明确开始测试时才建立推广活动和测试阶段。测试开始后不能跳日或退回待推广，只能测试继续、测试淘汰或测试接放量；放量期只能放量继续、放量淘汰或推广周期结束，历史日度阶段不被后续选择覆盖。
- 推广活动创建后修改实发日期属于破坏性重置：系统先展示受影响记录并二次确认，再在事务中删除该排期关联的推广日度数据、阶段和活动，按新实发日期回到待开始推广。
- 非推广复盘以实发日为锚点，按“首轮（约 7 天）→ 二轮（约 15 天）”顺序开放，提醒日不替代真实数据截止日。分类规则决定是否需要非推广复盘；“第一时间解析帖集”所有学科默认关闭，历史已完成事实不删除。
- 非推广节点允许填写原因后跳过，不要求笔记 ID 或指标；首轮跳过后二轮到期可继续，节点可以恢复，后续已完成节点保留。跳过不生成零值、不计入已复盘或同类基准，周会候选及新定稿同步识别该状态，已有快照不覆盖。
- Sidebar 在“复盘与沉淀”下使用“日度推广复盘 / 非推广复盘 / 例会总复盘”三个业务入口。“非推广复盘”独立承担原始数据与结论录入；推广周期汇总与分析统一进入“例会总复盘”，不建设独立的推广阶段复盘模块。
- 点击率和 3 秒阅读率直接保存百分比与数据截止日；结论选填。同类基准使用全部历史中相同学科、稳定分类和阶段的数据，包含当前帖，只展示客观统计。首次保存为 V0，后续更正生成 V1+。
- 非推广复盘使用“待复盘 / 已复盘 / 不复盘”视角，支持“学科 → 帖子分类”联动筛选，主体统一使用一行对应“帖子 × 复盘节点”的高密度表格；固定展示实验日期、帖子、分类、节点、点击率和 3 秒阅读率，笔记 ID 只作为帖子下方弱信息及 Inspector 详情。两项核心指标直接展示相对同类均值的 pp 差值，并以低饱和绿、灰、红辅助表达正向、中性、负向状态；同类均值与样本量保留在悬停说明。表格默认按实验日期倒序，支持实验日期和两项指标双向排序；行详情统一进入右侧 Inspector，移动端使用全屏。
- 小红书笔记 ID 只归属逻辑帖子 `operations_content.platform_note_id`，统一规范为去除首尾空格并转小写后的 24 位十六进制值，且全局唯一；全部内容版本、排期、Campaign、日度事实和复盘页面读取同一值，不复制进下游表或历史快照。
- 笔记 ID 不在实发时填写。推广帖允许先开始测试，首次保存推广日度复盘时必须与日度事实原子补齐；非推广帖首次保存任一复盘节点时必须与复盘事实原子补齐。已有 ID 默认只读；统一更正入口必须展示旧值、新值和全版本同步影响，并由服务端收到确认标记后更新。
- 周会非推广推荐榜按“排期 + 首轮/二轮”勾选：提醒日在会议区间内的节点默认勾选，其他截至区间结束日已到期节点可手动选择。指标待补不阻止定稿；进入过已定稿周会的节点显示复盘次数并允许二次复盘。
- 分类保持稳定 ID，显示名称、是否可选和默认推广身份通过左下角“系统设置”的带生效日期规则版本调整，只影响生效后的新建帖子。已有 Campaign 的帖子改为非推广时必须填写原因并确认影响；开放阶段受控结束，Campaign、日度事实和推广复盘保留。

## 技术基线

- 技术栈采用 Astro 5 + React 18 + TypeScript，项目及 Vercel 使用 Node 22；保留现有页面与业务结构。
- 包管理器采用 `pnpm`。
- 样式以 Astro scoped CSS 为主，复杂交互组件可以使用 React 和 CSS Modules。
- 首页内容集中维护在 TypeScript 配置中，避免正文散落在组件里。
- 公网使用独立 Vercel 项目和固定 HTTPS 域名，通过 CLI 手动发布；Git 不自动部署。
- 使用 Neon 托管 PostgreSQL、Drizzle ORM、标准 `postgres` 驱动和 Astro server 输出；首页显式静态生成。本机使用 Node adapter，公网使用 Vercel Node 函数；函数与当前 Neon 分支均在 us-east-1。
- 业务页面和接口使用 Better Auth 用户名登录与数据库会话，管理员／员工角色来自数据库，不接受客户端修改。注册关闭，账号通过受控脚本创建，密码只保存安全哈希；Basic Auth 不再作为兼容入口。
- 员工可查看业务数据和规划，录入／编辑排期、实发、指标与复盘（已有应发时间的改期需审批）；系统规则、年度规划写入／恢复、删除、已有笔记 ID 更正、删除或重建历史及改用途强制结束推广仅管理员可用。正常的日度推广决策仍属于日常操作。危险操作在事务内检查实际影响和管理员身份，并保留已有确认步骤。
- 两种角色共享团队业务数据。现有版本记录已验证的用户名，完整个人审计和细粒度权限后续单独确认。
- 公网与本地共用当前 Neon 分支，数据修改立即互通。结构变更先在临时分支验证，备份后做兼容迁移；测试不向共享库写入虚构数据。构建和部署不自动执行数据库迁移。
- 会话有效期 7 天，Cookie 使用 HttpOnly、SameSite=Lax，HTTPS 下启用 Secure；不使用客户端会话缓存。登录来源检查及数据库共享限流在多实例部署中生效；生产认证密钥与 Formward 独立。
- 当前建设两角色登录权限，独立后台、自动采集和报告生成仍需单独确认。

## 文档基线

- 仓库主要内容目录维护各自的 `README.md`，用于说明目录用途、文件职责和安全边界；`src/pages/` 除外，避免 Astro 把说明文档生成为新路由。
- `docs/` 使用 `README.md` 导航，长期结论仍只进入 `DECISIONS.md`、`DESIGN.md` 和 `ROADMAP.md`。
- 产品、结构和技术的已确认结论统一进入本文件。
