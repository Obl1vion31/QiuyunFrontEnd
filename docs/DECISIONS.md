# 已确认决定

本文件只记录已经确认、会影响后续工作的产品、结构和技术结论。

## 产品定位

- 当前产品暂称“前端团队管理系统”。
- 网站长期目标是承载前端业务工作、数据、规则、复盘和协作入口，不应停留在静态宣传页。
- 首页以部门工作流为主要叙事，呈现策划、内容、视觉、发布、用户触点和反馈回流如何组成完整流程；对外文案不强调个人或当前人员安排。
- 总枢纽首页是系统入口，不是整个系统，也不是实时业务驾驶舱。
- 前端负责从用户看见内容，到阅读、产生兴趣、形成咨询并完成有效交接的过程；最终销售成交仍属于销售侧边界。
- 原始业务数据不应主要存放在周报或月报中；报告是输出视图，不是事实来源。

## 当前页面边界

- 当前正式界面包含总枢纽首页、用户名登录、年度规划、排期、推广日度、推广阶段复盘、非推广复盘、例会与系统设置。
- 首页用于解释前端存在的意义、完整工作链路和后续系统入口。
- 首页首屏同时呈现工作台定位与前端使命：以 `FRONTEND CONTENT WORKSPACE` 说明平台属性，以 `WHY WE EXIST` 说明内容触达目标；不再设置独立的使命区块。
- 首页不展示实时数据、周报明细、月报明细、当前项目列表、完整业务排期或个人绩效薪资明细。
- 首页当前保留业务系统、组织与人员、绩效与报酬三个方向的入口概念。
- 业务系统入口连接 `/business/operations-schedule`；组织与人员、绩效与报酬继续保持占位或授权入口。
- 排期以“新做帖”和“改帖”区分内容生产动作：新做帖建立 V0，改帖从原版本派生 V1/V2 并保留版本链；“编辑排期”只更正资料、应发时间与用途，不代替改帖，也不承担实发登记。
- 创建改帖只填写一项“具体改动说明”，说明具体改动部分、改动原因与希望达到的效果；不再单独记录改动类型和修改目标。
- 帖子身份、内容版本和发布排期分别保存；历史排期不猜测关联，每条作为独立 V0。
- 学科与帖子分类是两个独立的固定字典，通过映射决定学科可用分类。TMUA 与 STEP 使用“出分合集”，面试课仍保留独立“喜报”；增加固定“临时帖”分类和“临时学科 / 临时帖”兜底组合，历史空分类归入临时帖；新建或编辑时必须选择有效分类，不强制绑定年度规划行。
- 年度细致规划行优先使用“学科 + 帖子分类”作为显示名称；帖集使用统一的 ` [帖集]` 后缀。机器关联始终以 `subject_id + category_id` 为准，不根据中文名称反查。
- 总周期规划位于具体内容排期上游，默认以一个自然年度页面同时展示总规划和各学科细致规划，不在当前阶段自动生成帖子、内容版本或排期。
- 年度规划以“学科分区 → 有序细致规划行 → 一个或多个时间块”组织。细致规划行复用现有学科与分类关系，以 `subject_id + category_id` 表达学科和帖子类别，不再填写或展示课程名称；数据库旧空列和历史快照字段只保留兼容。
- 总规划不作为可编辑规划行保存，而是从启用的细致规划自动汇总：全部启用时间块形成内容流动周期，块内付费区间形成付费推广周期；整行推广标记只保留兼容，不作为新汇总依据。旧总规划记录由受控迁移清理，不进入页面和计算；没有帖子来源的 G5 不建立细致规划或占位汇总。
- 时间块保存半月起止、可选阶段名称、自由备注和块内付费区间。同一行可以有多个不连续时间块但不能重叠；月中结束覆盖上半月，月中开始从下半月起算。页面不计算或显示数量公式，未确定内容可直接填写“待定”。班课全程推广、讲义与模考首月推广是配置策略，编辑器不据此限制用户调整。
- 年度规划的主要 HTTP/HTTPS 链接属于规划行，一行可以保存多个。所有有效修改生成包含规划行、时间块和链接的不可变版本快照，恢复历史时创建新版本，不覆盖旧历史。
- 年度规划新建为 V0，后续真实调整逐次追加版本，历史快照不可变；快照格式 v4 保存半月与付费区间，v2/v3 在读取和恢复时转换为新格式。历史初始化规则：新建规划行为 V0，首次实际修改后进入 V1。搭建与初始化记录按受控迁移归档为 V0，后续真实运营修改保留历史；该规则不改变内容发布排期自身的新做帖 V0 / 改帖 V1+ 版本链。
- 细致规划的显示顺序跟随帖子分类字典；停用行默认隐藏且不参与汇总。SOP 在矩阵中只显示链接箭头，链接名称不作为主要业务信息。
- 规划行唯一约束为同一年、同一分区、同名规划项目唯一；同一分类可以服务多个不同用途的规划行。正常新建不强制数量、分类、时间块或手填变更说明。
- 年度复制仅写入空白目标年度，复制年度说明、全部细致规划、启停状态、时间块、备注、付费区间与行级链接；新行使用独立 ID 和 V0，不复制来源版本链，不覆盖目标配置。复制与常规年度写入共用事务锁。
- 排期支持新做帖、编辑排期、独立实发登记、从原版本发起改帖和受保护删除，不支持通用上传导入或导出。删除只用于清理没有改帖版本链、推广活动、非推广指标、复盘、预约、发布留痕或用途变更记录的独立排期；删除时同步清理其唯一 V0 和帖子主体，存在任一下游数据时必须拒绝删除。
- 内容发布控制台已实现总周期规划、排期管理、日度推广复盘、非推广首轮/二轮复盘、推广阶段复盘和例会复盘；月/年汇总、独立数据填报和报表中心仍只显示规划状态。
- 内容发布控制台的异步交互统一由共享壳层提供动作文字、忙碌状态和防重复触发；页面专项反馈可以补充，但不能让存在等待时间的操作处于无提示状态。
- 排期管理默认使用月历，保留按日期分组时间轴台账；本月内容、待发和已发筛选保持当前显示方式，跨月待办使用台账；推广中不再作为独立看板，而是同一数据集的筛选视角，并拆分显示测试中与放量中数量。
- 桌面端使用 `Sidebar + Toolbar + Inspector + Sheet` 结构：Inspector 查看当前帖子详情和版本链，Sheet 承载新做帖、编辑排期和创建改帖；移动端导航转为底部 Bar。
- “推广”只指付费测试或放量内容；正在投放但没有跑出量的日子允许真实五项零值，并仍属于原测试／放量阶段。排期使用独立的 `is_promoted` 布尔字段稳定标识是否属于推广帖，对外状态统一为非推广、待发布、推广待开始、推广测试中、测试待定、推广中、推广暂停、推广结束、测试淘汰和放量淘汰；底层 `waiting_action` 按原阶段解释为测试待定或推广暂停，节假日暂停保留原阶段。结束、淘汰或等待期间仍保持 `is_promoted = true`。推广周期已结束表示内容未被淘汰而自然结束一轮推广，测试淘汰表示测试后停止投入，放量淘汰表示进入放量后停止投入。“推广中”表示放量状态，“推广进行中”作为测试中与放量中的聚合筛选。
- 测试待定／推广暂停支持逐帖选择起止日期，历史补录和未来安排均保存为状态区间，不生成零指标或未来事实。未来区间到开始日才生效，截止日包含当天；最后一天可安排下一步并明确次日生效日期，未安排时持续待定，只保留一项待安排提醒，不累计逐日待办。测试待定可继续／延长、恢复测试、开始放量或测试淘汰；推广暂停可继续／延长、恢复推广、放量淘汰或自然结束。旧逐日等待事实保留兼容，系统不按零消耗推断待定。员工与管理员均可安排正常区间和次日动作，涉及已有历史事实的调整由管理员预览影响并确认；范围编辑入口同时在历史总览中提供。
- 应发与实发精确到分钟并按 `Asia/Shanghai` 解释；实发通过独立登记入口保存，完成情况不由用户选择，而是自动归一化为待发布、按时发布或延期发布。满应发 8 小时进入延期第 1 天，以后每满 24 小时新增一天；每一天必填责任方（自身／需求端）和文字原因，实发登记原子补齐欠填理由。历史原因逐日复制，空原因填“未知”，责任方标记历史未确认并保留历史补齐来源。
- 发布统一登记发布时间、小红书帖子链接和项目文档；员工与管理员直接提交，不区分预约，也不审核或到点补链。允许未来时间，保存后立即显示已发送；发布时间、应发时间和登记操作时间分别保留。首次登记保留项目文档要求，推广仍按 T+1、非推广仍按发布时间后的节点开放。
- 所有新发布登记必须提供帖子链接，即使补登过去日期也一样。北京时间 2026 年 10 月 17 日零点以前已发送且链接为空的现存记录可继续留空；不产生补链待办，界面不显示缺失解释或占位文字。已有链接不能清空；更正为截止日之后的发布时间须提供链接。
- 帖子链接接受完整小红书分享文案，识别 xhslink.cn、xhslink.com 及小红书帖子长链接，保存纯链接并保留签名参数；多条不同有效链接须由用户保留一条。前后端共用规则，不抓取、自动核验或提取笔记 ID，项目文档与帖子链接独立。
- 员工可直接首次登记、补充或更正帖子链接；已有发布时间仅管理员凭原因更正，保留旧值、新值和操作者。发布修订号及事务锁防止并发覆盖，更正影响已有推广事实时保留影响确认。未来发布时间只要求已到期的逐日延期理由，后续随时间推进，最多累计到填写的发布时间。
- 月历按应发日期放置帖子；按时已发用绿色、延期已发用红色、暂未发用黄色，推广身份独立显示蓝色标签，非推广使用灰色标签。逾期未发保持黄色并明确标注。点击日期或当天空白区域使用共用新做帖窗口，预填当天日期，时分仍需选择；不增加时间待定状态。
- 旧预约只保留历史读取；旧写入接口登录校验后返回 410 并提示刷新，旧通知计数字段返回零。旧预约不自动转成已发送；通过统一发布登记后结束对应旧记录。已有历史和删除保护保留。
- employee 修改已有应发时间必须申请并经 admin 审批；批准前按原排期计时，批准后按新时间重新计时，旧逐日理由与欠填事项保留。admin 直接改期也填写理由，改期与审批均留存经验证的操作者和时间。团队共享延期、待补理由和审批队列；延期数量按排期记录计数，理由填完但未实发时仍显示延期。
- 新做帖、创建改帖和编辑排期允许项目文档链接为空；缺失文档在未实发阶段是正常的“待登记”状态。首次发布登记必须填写 HTTP/HTTPS 项目文档链接；历史已发更正时保留原文档状态。数据库保留可空的 `project_doc_name` 兼容历史数据。
- 一次性历史数据导入必须使用默认只读预检、显式写入、事务保护和幂等键；完成后移除批次脚本，不在核心文档保留具体文件名、月份、条数或清理结果。当前不建设通用上传或自动同步。
- 推广日度按 T+1 填写消耗、平台／实际开口与留资人数，自动计算实际开口和留资成本，不录入点击率。每日只列尚未完成的连续投放日期，按顺序处理；待定区间和完整节假日跳过，不生成指标。已填事实进入默认全部记录、日期可选的历史总览，支持帖子／日视角、筛选与 Inspector 更正。生命周期以最后已填事实为截止，使用全宽比例条及完整日期，测试黄、放量绿，不随未填日期继续增长。
- 已保存的推广日度事实允许登录账号更正消耗、四项人数和备注；下一步与生命周期更正仅管理员可执行；日期、帖子、活动和阶段快照保持系统只读。修改下一步且存在后续事实时，必须先展示影响数量并二次确认，再在事务中删除失效的后续事实及待定安排、重建阶段与活动状态，并同步排期推广状态；被删除日期重新进入连续待办队列。
- 推广帖填写实发日期后先进入“待开始推广”，不自动建立推广活动；日度待办可以把当天确认成“当日未推广”，只推进排期的确认日期游标，不生成空指标事实。明确开始测试时才建立推广活动和测试阶段。测试开始后不能跳日或退回待推广，只能测试继续、测试淘汰或测试接放量；放量期只能放量继续、放量淘汰或推广周期结束，历史日度阶段不被后续选择覆盖。
- 推广活动创建后修改实发日期属于破坏性重置：系统先展示受影响记录并二次确认，再在事务中删除该排期关联的推广日度数据、阶段和活动，按新实发日期回到待开始推广。
- 非推广复盘以实发日为锚点，按“首轮（约 7 天）→ 二轮（约 15 天）”顺序开放，提醒日不替代真实数据截止日。分类规则决定是否需要非推广复盘；“第一时间解析帖集”所有学科默认关闭，历史已完成事实不删除。
- 非推广节点允许填写原因后跳过，不要求笔记 ID 或指标；首轮跳过后二轮到期可继续，节点可以恢复，后续已完成节点保留。跳过不生成零值、不计入已复盘或同类基准，周会候选及新定稿同步识别该状态，已有快照不覆盖。
- Sidebar 在“复盘与沉淀”下只保留一个“推广帖复盘”；顶部为每日复盘／阶段复盘，每日内部提供历史总览。统一入口为 `/business/daily-promotion-review`，阶段使用 `?view=stage`，旧阶段路径保留参数重定向。非推广和例会独立。
- 阶段复盘完全自选日期，不限定自然周或固定 7 天。放量只汇总所选区间内的实际数据；测试以该段最后截止日归属区间，包含该段完整测试，即使开始日早于区间。按内容版本与阶段区分，不能仅按共用笔记 ID 合并；待定与暂停不计投放日，缺失数据明确标记，零分母成本显示“—”，成本由总消耗除以总人数计算。
- 推广阶段快照从 V0 起保存，重新生成追加 V1+，旧版本不变；快照保存来源日度事实与缺口，提供可截图的紧凑汇总。阶段模块不展示点击率；例会点击率手动补充，不改变非推广点击率。
- 例会分为本周动向、推广阶段复盘快照、非推广复盘快照、临时事项快照、本周结论与遗留／待解决事项五部分。本周动向从会议日期内已录入的测试和放量事实生成，情况与策略人工填写；推广绑定指定快照版本，非推广冻结选中节点当时的指标、同类基准和结论，待补不填零。临时事项支持文字、HTTP/HTTPS 链接及上传／粘贴图片，图片私有保存于现有数据库，经认证接口读取。例会定稿由服务端组装事实，不接受客户端提供指标快照；修订追加版本，既有定稿与引用不随源数据更正变化，旧 v2 快照继续可读。
- 点击率和 3 秒阅读率直接保存百分比与数据截止日；结论选填。同类基准使用全部历史中相同学科、稳定分类和阶段的数据，包含当前帖，只展示客观统计。首次保存为 V0，后续更正生成 V1+。
- 非推广复盘使用“待复盘 / 已复盘 / 不复盘”视角，支持学科与分类筛选。已复盘额外提供全部／首轮／二轮和按帖子分组，默认全部轮次且按实发排期版本分组，组内首轮、二轮相邻，缺失不填零。同类基准仍按全部历史中的同学科、同分类和同轮次计算并包含当前帖，筛选不改变样本池；明示均值、样本量与 pp 差值。默认实验日期倒序；分组的指标排序须先选择单轮，取消分组可逐行排序。待复盘节点、日期和填写／跳过／恢复规则保持现有口径。
- 非推广分组只改变数据组织；开启与关闭共用相同六列表格，原位切换并保留公共界面、滚动和详情。整个工作台遵守统一视觉和交互基准，具体规则见 `DESIGN.md`，协作与验收约束见项目级 `AGENTS.md`；后续按明确任务逐步收敛，不借规范建设扩大重构范围。
- 完整日期时间统一为日期选择＋时间选择，日期在左、时间在右；排期、发布登记、员工改期申请和例会沿用同一共享输入，原提交字段、业务必填、默认值、服务端时间解析及已存精确时间保持原口径。仅日期的筛选／复盘区间不增加时间。
- 工作台遵循语义先行、全局同步与局部例外：同类表单、日期表达、标题及容器共用规则，优化时同步全部适用消费者；允许业务结构与合理密度差异，用户限定的局部范围优先。
- 非推广展示方式使用独立的“按帖子分组 / 不分组”互斥切换，与学科、分类及轮次筛选分组排列。编辑排期、发布登记复用同一表单抽屉及控件规范，固定头部与操作区，仅正文滚动；字段、提交、权限与数据规则沿用原有流程。
- 小红书笔记 ID 只归属逻辑帖子 `operations_content.platform_note_id`，统一规范为去除首尾空格并转小写后的 24 位十六进制值，且全局唯一；全部内容版本、排期、Campaign、日度事实和复盘页面读取同一值，不复制进下游表或历史快照。
- 笔记 ID 不在实发时填写。推广帖允许先开始测试，首次保存推广日度复盘时必须与日度事实原子补齐；非推广帖首次保存任一复盘节点时必须与复盘事实原子补齐。已有 ID 默认只读；统一更正入口必须展示旧值、新值和全版本同步影响，并由服务端收到确认标记后更新。
- 周会非推广推荐榜按“排期 + 首轮/二轮”勾选：提醒日在会议区间内的节点默认勾选，其他截至区间结束日已到期节点可手动选择。指标待补不阻止定稿；进入过已定稿周会的节点显示复盘次数并允许二次复盘。
- 分类保持稳定 ID，显示名称、是否可选和默认推广身份通过左下角“系统设置”的带生效日期规则版本调整，只影响生效后的新建帖子。已有 Campaign 的帖子改为非推广时必须填写原因并确认影响；开放阶段受控结束，Campaign、日度事实和推广复盘保留。

- 付费推广从放量回到重新测试表示内容已修改，必须派生下一内容版本及独立排期／推广周期；新旧版本共用逻辑帖子笔记 ID，项目链接可沿用。历史复测使用真实开始日期，时分缺失时采用用户已确认的占位并注明来源，不编造具体修改内容。
- 明确的测试结束至放量开始间隔按测试待定区间保存，不伪造零指标；同阶段未跑出量的日期在确认后补五项零值。原始指标和区间共同回放，零分母成本显示未知。
- 员工与管理员均可一键暂停、调整截止日或提前恢复，记录已验证的账号与时间。只将正在测试／放量的活动纳入本批目标，原本等待的内容保持状态与原因；截止日包含当天，次日上海时间零点仅恢复本批原阶段。
- 节假日完整暂停日不进入复盘待办、不生成指标；暂停当日及提前恢复当天仍保留真实投放复盘。既有等待内容在完整假期内也无需逐日确认，假期后保持原状态。开始／恢复接口受全局暂停约束，历史补录不能绕过暂停。
- 节假日暂停只管理工作台的状态、历史和复盘待办，广告平台投放需同步操作；不接入未经确认的第三方自动停投。

## 技术基线

- 技术栈采用 Astro 5 + React 18 + TypeScript，项目及 Vercel 使用 Node 22；保留现有页面与业务结构。
- 包管理器采用 `pnpm`。
- 样式以 Astro scoped CSS 为主，复杂交互组件可以使用 React 和 CSS Modules。
- 首页内容集中维护在 TypeScript 配置中，避免正文散落在组件里。
- 公网使用独立 Vercel 项目和固定 HTTPS 域名，通过 CLI 手动发布；Git 不自动部署。
- 开发与修正先推送工作分支，用户最终验收通过后再合入 `main`；推送工作分支不代表已经合并主分支。
- 使用 Neon 托管 PostgreSQL、Drizzle ORM、标准 `postgres` 驱动和 Astro server 输出；首页显式静态生成。本机使用 Node adapter，公网使用 Vercel Node 函数；函数与当前 Neon 分支均在 us-east-1。
- 业务页面和接口使用 Better Auth 用户名登录与数据库会话，管理员／员工角色来自数据库，不接受客户端修改。注册关闭，账号通过受控脚本创建，密码只保存安全哈希；Basic Auth 不再作为兼容入口。
- 员工可查看业务数据和规划，录入／编辑排期、首次发布、帖子链接、指标与复盘（已有应发时间的改期需审批；已有发布时间更正仅管理员处理）；系统规则、年度规划写入／恢复、删除、已有笔记 ID 更正、删除或重建历史及改用途强制结束推广仅管理员可用。正常的日度推广决策仍属于日常操作。危险操作在事务内检查实际影响和管理员身份，并保留已有确认步骤。
- 两种角色共享团队业务数据。现有版本记录已验证的用户名，完整个人审计和细粒度权限后续单独确认。
- 公网与本地共用当前 Neon 分支，数据修改立即互通。结构变更先在临时分支验证，备份后做兼容迁移；测试不向共享库写入虚构数据。构建和部署不自动执行数据库迁移。
- 会话有效期 7 天，Cookie 使用 HttpOnly、SameSite=Lax，HTTPS 下启用 Secure；不使用客户端会话缓存。登录来源检查及数据库共享限流在多实例部署中生效；生产认证密钥与 Formward 独立。
- 当前建设两角色登录权限，独立后台、自动采集和报告生成仍需单独确认。

## 文档基线

- 仓库主要内容目录维护各自的 `README.md`，用于说明目录用途、文件职责和安全边界；`src/pages/` 除外，避免 Astro 把说明文档生成为新路由。
- `docs/` 使用 `README.md` 导航，已确认规则、设计与优先级分别进入 `DECISIONS.md`、`DESIGN.md` 和 `ROADMAP.md`；最新交接滚动维护在根 `handoff.md`，专题文件负责代码定位及操作指南，历史记录集中在 `archive/`。
- 产品、结构和技术的已确认结论统一进入本文件。
- 视觉与交互规则只在方向获得确认后进入 `DESIGN.md`。
- 当前工作、下一步与暂缓事项进入 `ROADMAP.md`。
- 不重复维护产品定义、结构现状和阶段总结；日常计划在会话展示，常规结果由 Git 与交付回复记录。用户明确要求保存的历史资料进入归档，不作为当前规则依据。
- phase 02、phase 03 和 phase 04 的执行计划或结果文档，是用户明确要求长期保存的例外。
