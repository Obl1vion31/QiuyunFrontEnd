# 当前阶段总结

> 更新时间：2026-07-27  
> 用途：为下一阶段规划提供统一上下文。本文总结当前仓库中已经确认的方向和已经存在的实现，不代表下一阶段范围已经获得批准。

## 一、结论摘要

项目目前已经从“静态展示首页”进入“总枢纽首页 + 第一个真实业务 MVP”的阶段。

- 总枢纽首页已经形成明确的“内容穿越总控台”视觉方向，但仍处于多设备和真实素材观感验收阶段。
- 内容发布控制台的“排期管理”已经具备真实数据库读写、新做帖、改帖版本链、编辑、状态筛选、台账和月历等核心能力。
- 日粒度全量复盘、阶段复盘和报表中心目前只有导航占位，尚未建设实际数据能力。
- 数据层使用 Neon 托管 PostgreSQL 和 Drizzle ORM，核心模型已经拆分为帖子身份、内容版本和发布排期，另有学科、帖子分类及二者的可用关系。
- 当前认证只是临时多账号 HTTP Basic Auth；没有正式登录、细粒度权限和操作者审计。
- 当前只进行本地验收，没有生产部署流程。

## 二、当前视觉设计

### 2.1 整体视觉策略

当前不是整站统一使用强动效，而是有意区分两类界面：

1. **总枢纽首页**是全站唯一允许大胆视觉表达的页面。
2. **业务页面和首页后半段**强调简洁、低动效、高信息密度和中文可读性。

这意味着后续业务模块不应直接复制首页的 3D 穿越效果，而应延续清晰的工作台结构。

### 2.2 总枢纽首页

首页采用“内容穿越总控台”概念：

- 深色 Hero 以 `Control Night #0B1B2B` 为基础空间。
- 八张真实的 3:4 内容封面分布在不同深度，随正常页面滚动从远处向前穿过工作台。
- 初始构图通过内外两层、顺时针顺序和轻微尺寸递增形成静态螺旋感；滚动后回到向前展开的轨迹，不围绕中心旋转。
- 六条流程轨道表达策划、内容、视觉、发布、用户触点和复盘的连续工作流。
- Hero 同时表达“平台是什么”和“内容为了什么”，并保留三项核心宗旨：愿意点击、愿意读完、愿意进一步了解或咨询。
- 远处封面降低亮度并轻微模糊，统一遮罩和局部暗角保障主标题、使命和轨道的可读性。
- Hero 后由浅蓝灰的工作流阅读区和明亮的系统入口自然承接，不覆盖 Hero。
- 动效使用轻量 React Island 和 CSS 3D，没有引入大型 3D 库；支持 `prefers-reduced-motion`，移动端会降低封面尺寸、运动强度和轨道密度。

当前颜色系统包括：

| 变量 | 色值 | 主要用途 |
| --- | --- | --- |
| Control Night | `#0B1B2B` | Hero 空间、页脚 |
| Signal White | `#F5F7F4` | 页面底色、主要文字 |
| Blueprint | `#5B8CFF` | 环境光、轨道、结构信息 |
| Marker Coral | `#FF8A68` | 当前流程、关键动作 |
| Monitor Mint | `#9ED8C4` | 用户触点、辅助状态 |
| Workflow Mist | `#E9EFF2` | Hero 后的阅读区 |

首页方向和主要实现已经形成，目前仍需完成：

- 八张真实封面在不同色彩和文字密度下的遮罩、对比度检查；
- 桌面端、移动端和减少动态效果模式的实际滚动验收；
- 根据验收结果微调深度、尺寸和运动参数。

### 2.3 内容发布控制台

业务页采用高密度运营台账风格，并吸收 Apple Design 的层级和反馈原则，但不仿制 macOS。

当前结构为：

- 桌面端：`Sidebar + Toolbar + Inspector + Sheet`；
- 主区域：按日期分组的紧凑时间轴台账，可切换月历；
- Inspector：查看当前内容详情、发布状态和版本关系；
- Sheet：承载新做帖、编辑排期和创建改帖；
- 移动端：导航转为底部 Bar，Inspector 和 Sheet 使用全屏形式。

半透明材质只用于工具栏、Inspector、Sheet 等功能性上层；密集数据区使用实色和明确对比。延期、逾期、数据库错误和字段错误都有文字提示，不只依靠颜色区分。

该控制台已经完成主要界面重构，但仍需在真实大数据量下验收桌面端和移动端的信息密度、滚动与操作体验。

## 四、当前数据库形式

### 4.1 技术形式

当前数据库是 **Neon 托管的 PostgreSQL 关系型数据库**，通过 Drizzle ORM 定义结构和读写，通过 `drizzle/` 下的 SQL 迁移管理结构变化。

- 动态排期页和 API 在服务端访问数据库；
- 数据库连接采用标准 `postgres` 驱动；
- `.env` 中的 `DATABASE_URL` 应指向隔离的 Neon 开发分支；
- 数据库连接串不会进入浏览器端代码；
- 新增或编辑业务数据保存后立即生效，不需要重新迁移或构建；
- 当前总结只依据仓库 schema、迁移和代码，不读取或统计真实 Neon 数据。

### 4.2 核心数据模型

```text
operations_subject（学科）
  └─< operations_subject_category >─ operations_category（帖子分类）
                 │
                 └─ 约束某个学科可选择哪些分类

operations_content（帖子身份）
  └─< operations_content_version（内容版本 V0 / V1 / V2 ...）
          ├─ source_version_id ──> operations_content_version（来源版本，自关联）
          ├─ subject_id ─────────> operations_subject
          ├─ category_id ────────> operations_category
          └─< operations_content_schedule（发布排期）
```

六张主要表的职责如下：

| 表 | 作用 | 关键关联或约束 |
| --- | --- | --- |
| `operations_subject` | 学科固定字典 | 被内容版本和学科分类映射引用 |
| `operations_category` | 通用帖子分类固定字典 | 被内容版本和学科分类映射引用 |
| `operations_subject_category` | 学科可用分类的多对多映射 | 复合主键为 `subject_id + category_id` |
| `operations_content` | 稳定的帖子身份 | 一个帖子可以拥有多个内容版本 |
| `operations_content_version` | 某个帖子的具体版本和内容资料 | 关联帖子身份、学科、分类；通过 `source_version_id` 自关联形成版本链 |
| `operations_content_schedule` | 某个内容版本的发布与推广安排 | 关联具体内容版本，保存应发/实发时间、推广状态和完成状态 |

### 4.3 最重要的业务关联

#### 帖子身份、版本和排期分离

这是当前最核心的数据设计：

```text
同一个 operations_content
  ├─ V0：新做帖
  │    └─ 对应发布排期
  ├─ V1：从 V0 派生的改帖
  │    └─ 对应新的发布排期
  └─ V2：继续派生的改帖
       └─ 对应新的发布排期
```

- `operations_content` 回答“这是同一个帖子系列吗”；
- `operations_content_version` 回答“这是这个帖子的哪一个版本，内容资料是什么”；
- `operations_content_schedule` 回答“这个版本什么时候发布、是否实发、处于什么推广状态”。

编辑排期只修改现有记录，不创建新版本；创建改帖才派生新版本。历史排期不猜测相互关系，而是分别作为独立 V0 保存。

#### 版本来源自关联

`operations_content_version.source_version_id` 指向另一条内容版本，用来记录改帖来源。`content_id + version_number` 具有唯一约束，避免同一帖子出现重复版本号。

当前界面和读取逻辑主要按来源版本展示版本关系。后续如果要支持复杂分支、合并或一个版本对应多条发布排期，需要先明确业务规则，不能直接假设现有链式模型已经覆盖。

#### 学科与帖子分类

学科和分类是两个独立字典，通过 `operations_subject_category` 决定可用组合：

- TMUA：可使用全部 12 类；
- STEP：可使用除“冲刺班”外的 11 类；
- 面试课：当前不配置分类，允许 `category_id` 为空。

数据库同时使用复合外键和检查约束保护这一规则，前端选择控件和服务端 Zod 校验也会重复校验，避免只依赖界面。

#### 排期与业务状态

排期保存：

- 是否同步朋友圈；
- 推广状态；
- 应发时间；
- 实发时间；
- 系统归一化后的完成状态；
- 延期原因；
- 可用于一次性导入幂等去重的 `source_key`。

月份不单独保存，而是从 `planned_publish_at` 按上海时区推导。完成状态也不是自由选择，而是根据应发和实发时间计算。尚未实发但超过 12 小时在界面上显示为“逾期未发”，它是运行时视图，不是新增的持久化状态。

### 4.4 当前数据库边界

- 目前数据库只服务内容发布排期 MVP，不是全系统统一数据平台；
- 当前没有用户、角色、权限、审计日志、组织、绩效或薪资相关表；
- 当前没有自动采集和第三方同步数据模型；
- 当前没有为日粒度复盘、阶段复盘或报表中心确认指标表；
- 没有读取真实数据库，因此本文不对当前数据条数、完整率或线上状态作结论。

## 五、给下一阶段规划的关键提醒

1. 下一阶段规划应把“排期管理 MVP 验收”和“新建复盘/报表能力”分开，不要把已存在的导航占位当成已有功能。
2. 若进入复盘或报告阶段，应先确认事实数据、指标口径、填报责任、时间粒度、权限和报告输出，再设计新表或页面。
3. 新数据能力应继续遵守“原始业务数据是事实来源，报告只是输出视图”的原则。
4. 正式多人协作会影响认证、权限、操作者审计和数据归属，应作为独立范围规划。
5. 排期删除、通用导入导出、外部同步、部署和大范围数据模型调整均未获当前范围批准，实施前需要单独确认。
6. 总枢纽首页不是整个系统，也不是实时业务驾驶舱；新业务能力应进入独立模块，不应继续堆到首页。
7. 首页可保持鲜明视觉表达，新的业务页面应延续清晰、低动效、高密度和可访问的工作台原则。
