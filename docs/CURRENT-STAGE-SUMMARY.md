## 二、当前视觉设计

### 2.1 整体视觉策略

当前不是整站统一使用强动效，而是有意区分两类界面：

1. **总枢纽首页**是全站唯一允许大胆视觉表达的页面。
2. **业务页面和首页后半段**强调简洁、低动效、高信息密度和中文可读性。

这意味着后续业务模块不应直接复制首页的 3D 穿越效果，而应延续清晰的工作台结构。

### 2.2 总枢纽首页

首页采用“内容穿越总控台”概念：

- 深色 Hero 以 `Control Night #0B1B2B` 为基础空间。
- 八张真实的 3:4 内容封面分布在不同深度，随正常页面滚动从远处向前穿过工作台。
- 初始构图通过内外两层、顺时针顺序和轻微尺寸递增形成静态螺旋感；滚动后回到向前展开的轨迹，不围绕中心旋转。
- 六条流程轨道表达策划、内容、视觉、发布、用户触点和复盘的连续工作流。
- Hero 同时表达“平台是什么”和“内容为了什么”，并保留三项核心宗旨：愿意点击、愿意读完、愿意进一步了解或咨询。
- 远处封面降低亮度并轻微模糊，统一遮罩和局部暗角保障主标题、使命和轨道的可读性。
- Hero 后由浅蓝灰的工作流阅读区和明亮的系统入口自然承接，不覆盖 Hero。
- 动效使用轻量 React Island 和 CSS 3D，没有引入大型 3D 库；支持 `prefers-reduced-motion`，移动端会降低封面尺寸、运动强度和轨道密度。

首页方向和主要实现已经形成，目前仍需完成：

- 桌面端、移动端和减少动态效果模式的实际滚动验收；
- 根据验收结果微调深度、尺寸和运动参数。

### 2.3 内容发布控制台

业务页采用高密度运营台账风格，并吸收 Apple Design 的层级和反馈原则，但不仿制 macOS。

当前结构为：

- 桌面端：`Sidebar + Toolbar + Inspector + Sheet`；
- 主区域：按日期分组的紧凑时间轴台账，可切换月历；
- Inspector：查看当前内容详情、发布状态和版本关系；
- Sheet：承载新做帖、编辑排期和创建改帖；
- 移动端：导航转为底部 Bar，Inspector 和 Sheet 使用全屏形式。

半透明材质只用于工具栏、Inspector、Sheet 等功能性上层；密集数据区使用实色和明确对比。延期、逾期、数据库错误和字段错误都有文字提示，不只依靠颜色区分。

该控制台已经完成主要界面重构，但仍需在真实大数据量下验收桌面端和移动端的信息密度、滚动与操作体验。

Daily Promotion Review 作为排期控制台的推广复盘工作区：

- 只呈现标记为推广的帖子，每篇帖子一条生命周期泳道；
- 实发当天进入测试期，员工在下一天填写上一天数据；
- 测试期支持继续、淘汰、接放量，放量期支持继续、淘汰、正常结束；
- 状态决定从数据日的下一天生效，历史阶段不被覆盖；
- 修改实发日期或取消推广身份时，确认后删除该活动及全部日度事实并从新日期重新开始。

### 2.4 THE PLAN 年度总周期规划

`THE PLAN` 使用一张高密度年度矩阵同时展示总规划、TMUA、STEP 和面试课：

- 左侧固定显示规划分区、SOP 箭头和规划项目，右侧为 1—12 月；
- 总规划和细致规划共用固定业务列与 12 个月份轨道，临界宽度和窄屏允许横向滚动；
- 总规划位于细致规划上方，属于只读汇总结果，不提供编辑入口；
- 1、4、7、10 月建立季度起点分隔，点击规划后整行与 Inspector 同步选中；
- TMUA 使用蓝色、STEP 使用紫色、面试课使用橙色；
- 具体条幅只显示 `1×4`、`2×6`、`3+3+4` 等数量规则，不重复规划名称或阶段名称；
- 数量待确认的时间块显示 `?`；Inspector 和版本历史明确写出“数量待确认”，阶段名称仍可在 Inspector、编辑器、悬停说明和版本历史中查看；
- SOP 在固定列中以箭头表示，停用规划默认隐藏。
- Inspector 使用同月份比例的年度缩略轨道，并按身份、状态、时间块、SOP、备注和版本历史组织详情。

页面交互顺序是：

```text
选择年份
→ 查看自动总规划
→ 纵向浏览三个学科
→ 横向读取月份和数量规则
→ 点击规划项目或条幅查看 Inspector
→ 编辑规划或查看、恢复历史版本
```

## 四、当前数据库形式

### 4.1 技术形式

当前数据库是 **Neon 托管的 PostgreSQL 关系型数据库**，通过 Drizzle ORM 定义结构和读写，通过 `drizzle/` 下的 SQL 迁移管理结构变化。

- 动态排期页和 API 在服务端访问数据库；
- 数据库连接采用标准 `postgres` 驱动；
- 当前本地 `.env` 的 `DATABASE_URL` 指向用户建立的 Neon development 环境；具体分支名称仍以 Neon Console 的 Branches 页面为最终判断依据；
- 数据库连接串不会进入浏览器端代码；
- 新增或编辑业务数据保存后立即生效，不需要重新迁移或构建；
- 本次总结已对当前连接数据库执行只读表数量和字典查询，没有输出连接串或密码。

### 4.2 Development 与 Production

Neon development 是从 production 某个时刻创建的独立数据库分支。创建后两边独立变化：

```text
production（稳定数据）
    └── 创建 development
            ├── 测试迁移
            ├── 调整结构
            └── 录入测试或待审核业务数据
```

- development 中执行迁移、修改数据或删除内容，不会影响 production；
- production 后续新增的数据，也不会自动出现在既有 development 中；
- development 可以重置到 parent，但重置会覆盖 development 自己的修改；
- 上线通常不是把 development 改名为 production，而是在 development 验证后，将同一套代码和迁移应用到 production；
- migration 只处理结构和迁移文件明确包含的数据修正，development 中通过页面录入的业务数据不会自动复制到 production；
- 需要上线的业务数据应另行审核，再通过受控脚本、导入流程或人工录入迁移；
- production 建议启用 protected branch 并使用独立生产连接串，本地继续连接 development。

### 4.5 最重要的业务关联

#### 帖子身份、版本和排期分离

这是当前最核心的数据设计：

```text
同一个 operations_content
  ├─ V0：新做帖
  │    └─ 对应发布排期
  ├─ V1：从 V0 派生的改帖
  │    └─ 对应新的发布排期
  └─ V2：继续派生的改帖
       └─ 对应新的发布排期
```

- `operations_content` 回答“这是同一个帖子系列吗”；
- `operations_content_version` 回答“这是这个帖子的哪一个版本，内容资料是什么”；
- `operations_content_schedule` 回答“这个版本什么时候发布、是否实发、处于什么推广状态”。

编辑排期只修改现有记录，不创建新版本；创建改帖才派生新版本。历史排期不猜测相互关系，而是分别作为独立 V0 保存。

#### 版本来源自关联

`operations_content_version.source_version_id` 指向另一条内容版本，用来记录改帖来源。`content_id + version_number` 具有唯一约束，避免同一帖子出现重复版本号。

当前界面和读取逻辑主要按来源版本展示版本关系。后续如果要支持复杂分支、合并或一个版本对应多条发布排期，需要先明确业务规则，不能直接假设现有链式模型已经覆盖。

#### 学科与帖子分类

学科和分类是两个独立字典，通过 `operations_subject_category` 决定可用组合：

- TMUA：使用原有共享分类映射；
- STEP：使用除“冲刺班”外的原有共享分类映射；
- 面试课：使用面试课、推广讲义帖、成功案例、喜报、面试信息、面试准备须知和创新帖七类。历史内容允许分类为空，新建或编辑时必须选择。

数据库同时使用复合外键和检查约束保护这一规则，前端选择控件和服务端 Zod 校验也会重复校验，避免只依赖界面。

#### 排期与业务状态

排期保存：

- 是否同步朋友圈；
- 推广状态；
- 应发时间；
- 实发时间；
- 系统归一化后的完成状态；
- 延期原因；
- 可用于一次性导入幂等去重的 `source_key`。

月份不单独保存，而是从 `planned_publish_at` 按上海时区推导。完成状态也不是自由选择，而是根据应发和实发时间计算。尚未实发但超过 12 小时在界面上显示为“逾期未发”，它是运行时视图，不是新增的持久化状态。

#### 年度规划行、时间块与自动总规划

`operations_annual_plan` 是细致规划的稳定行身份，关联年度、分区、可选学科、可选分类、状态和推广汇总标记。

```text
规划行
  ├─ 时间块 A：3—7 月，弹性频次 1×5
  ├─ 时间块 B：11—12 月，弹性频次 1×2
  ├─ SOP 链接
  └─ V0 / V1 / V2 历史快照
```

- 时间块宽度由开始月份和结束月份决定，代表真实覆盖周期；条幅文字只显示数量规则；
- 弹性频次保存“每月默认篇数”，展示为 `每月频次 × 块长度`；
- 硬性组合保存正整数数组，例如 `[3,3,4]`，展示为 `3+3+4`；
- 数量尚未确认时保持数据库空值，主矩阵显示 `?`，不把未知值伪造成业务数字；
- 阶段名称与数量规则可以同时存在，但名称不在主矩阵条幅中重复；
- 同一规划行的时间块不能重叠，但可以不连续；
- 总规划不重复存储时间块，而是在页面查询时计算启用明细行的月份并集；
- `counts_toward_promotion` 只决定该行是否进入推广周期汇总，不改变条幅颜色。

#### 年度规划版本历史

当前初始化内容统一为 V0。用户确认开始实际运营修改后，任何规划行、分类关联、状态、推广标记、时间块、链接或备注变化都会：

1. 更新规划行当前状态；
2. 将完整“规划行 + 时间块 + 链接”保存为新快照；
3. 记录版本号、修改时间、Basic Auth 用户名、调整说明和差异；
4. 恢复旧版本时再创建一个新版本，不覆盖已有历史。

年度规划版本和帖子内容 V0/V1 版本链相互独立，两者解决不同业务问题。2026 年 7 月 28 日以前搭建和初始录入产生的年度规划 V1/V2/V3 已折叠为每条规划唯一的当前 V0，不视为正式业务修改历史。

### 4.6 当前数据库交互形式


| 用户操作     | 页面/接口行为                      | 数据结果             |
| -------- | ---------------------------- | ---------------- |
| 切换年份     | 服务端读取年度说明、规划行、时间块和链接         | 不写数据库            |
| 新建规划行    | Dialog 提交到年度规划 API           | 新建当前行、子记录和 V0 快照 |
| 编辑规划行    | 携带当前版本号提交并进行并发校验             | 事务更新并生成下一版本      |
| 新增/删除时间块 | 随规划行整体保存                     | 替换当前子记录，历史快照仍保留  |
| 打开 SOP   | 新窗口访问已校验 URL                 | 不写数据库            |
| 停用规划行    | 更新 `is_active`               | 默认隐藏且不进入自动汇总     |
| 标记推广     | 更新 `counts_toward_promotion` | 自动推广周期随之变化       |
| 查看历史     | 读取版本列表或具体快照                  | 不写数据库            |
| 恢复历史     | 读取旧快照并生成新当前版本                | 不覆盖历史            |
| 新做帖      | 创建帖子身份、V0 和发布排期              | 三层数据在事务中写入       |
| 创建改帖     | 从来源版本派生 V1+ 和新排期             | 保留来源版本关系         |
| 编辑排期     | 更新当前内容资料与排期                  | 不创建内容版本          |


所有年度规划写入均使用 Zod 服务端校验、Drizzle/PostgreSQL 事务、学科分类关系校验、月份范围校验、时间块重叠校验和 HTTP/HTTPS URL 校验。

### 4.7 当前数据库边界

- 目前数据库服务年度总周期规划和内容发布排期，不是全系统统一数据平台；
- 当前没有用户、角色、权限、审计日志、组织、绩效或薪资相关表；
- 当前没有自动采集和第三方同步数据模型；
- 当前没有为日粒度复盘、阶段复盘或报表中心确认指标表；
- 本文记录的是当前 development 分支的只读统计，不代表 production 数据状态；
- 当前没有自动把 development 业务数据发布到 production 的同步机制。

## 五、给下一阶段规划的关键提醒

1. 下一阶段规划应把“排期管理 MVP 验收”和“新建复盘/报表能力”分开，不要把已存在的导航占位当成已有功能。
2. 若进入复盘或报告阶段，应先确认事实数据、指标口径、填报责任、时间粒度、权限和报告输出，再设计新表或页面。
3. 新数据能力应继续遵守“原始业务数据是事实来源，报告只是输出视图”的原则。
4. 正式多人协作会影响认证、权限、操作者审计和数据归属，应作为独立范围规划。
5. 排期删除、通用导入导出、外部同步、部署和大范围数据模型调整均未获当前范围批准，实施前需要单独确认。
6. 总枢纽首页不是整个系统，也不是实时业务驾驶舱；新业务能力应进入独立模块，不应继续堆到首页。
7. 首页可保持鲜明视觉表达，新的业务页面应延续清晰、低动效、高密度和可访问的工作台原则。
