# Phase 04：THE PLAN 实施结果与下一轮优化方向

本文记录 Phase 04 已经完成的年度总周期规划能力、当前 development 数据审查，以及仍属于 Phase 04 的下一轮优化 Plan。它不表示进入下一模块，也不替代 `docs/DECISIONS.md` 中的长期结论。

> 状态：Phase 04 持续进行中。当前所有年度规划仍属于初始化 V0；在用户明确确认进入实际运营修改前，后续初始数据整理不应产生正式业务版本。

## 一、Phase 04 已完成内容

### 1. 年度总览

- 已建立 `/business/annual-plan` 年度总周期规划入口；
- 支持年份前后切换、年度说明和最近更新时间；
- 一个页面同时展示总规划、TMUA、STEP 和面试课；
- 细致规划按照学科纵向排列，横向展示 1—12 月；
- 桌面宽屏优先同时显示完整 12 个月，窄屏允许横向滚动。

### 2. 自动总规划

- 总规划已经改为从启用的细致规划实时汇总；
- 发帖周期取学科全部启用规划行的月份并集；
- 推广周期取启用且标记“计入推广周期”的规划行月份并集；
- 总规划是只读结果，不再提供普通规划行编辑器；
- 旧总规划记录仍保留在 development 数据库，但当前页面不读取，也不参与自动汇总。

### 3. 规划行和时间块

- 一条细致规划行可以关联学科和帖子分类；
- 一条规划行支持多个不连续时间块；
- 同一规划行的时间块不能重叠；
- 时间块支持弹性频次、硬性组合或暂时无数量规则；
- 条幅颜色只表示科目：TMUA 蓝、STEP 紫、面试课橙；
- 主矩阵条幅只显示 `1×4`、`2×6`、`3+3+4` 等数量表达，不重复阶段名称；
- 完整阶段名称仍保留在 Inspector、编辑器、悬停说明和版本快照中。

### 4. 链接和版本

- 一条规划行支持多个 HTTP/HTTPS SOP 链接；
- 矩阵中的 SOP 使用箭头入口，不重复显示链接名称；
- 每个规划版本保存规划行、时间块和链接的完整快照；
- 历史恢复通过生成后续版本完成，不覆盖已有历史；
- 初始化期间产生的 V1/V2/V3 中间历史已经清理，每条规划只保留当前内容并统一归档为 V0；
- 第一次真实运营修改才应从 V0 进入 V1。

### 5. 已完成的数据初始化

- 已建立 TMUA、STEP、面试课三个学科；
- 已建立 15 项帖子分类和 30 项学科—分类有效关系；
- 已将原始年度规划表录入 development；
- 已完成规划名称、帖集后缀和面试课分类统一；
- development 当前有 37 条规划行、51 个时间块和 37 个 V0 初始化快照。

## 三、总规划与细致规划的数据结构结论

### 推荐结论

总规划和细致规划不应继续作为两种可编辑业务记录共同保存在 `operations_annual_plan` 中。

推荐结构：

```text
operations_annual_plan_year
  年度说明

operations_annual_plan
  只保存可编辑的细致规划行
    ├─ operations_annual_plan_block
    ├─ operations_annual_plan_link
    └─ operations_annual_plan_version

自动总规划
  查询时由细致规划计算
  不保存成普通规划行
```

原因：

1. 总规划是细致规划的派生结果，不是独立事实来源；
2. 同时保存两份会产生不一致风险；
3. 总规划不需要 SOP、分类、课程、数量规则和版本编辑器；
4. `subject_id` 和 `category_id` 为空并不是数据库损坏，而是旧通用规划行无法套入细致规划关联结构的结果；
5. 自动汇总已经能够替代前六条旧总规划记录。

如果未来报表或性能需要数据库层复用总规划，可以考虑建立 PostgreSQL View 或专用只读查询，但当前数据量不需要提前建设。

### `course_name` 的建议

`course_name` 当前全部为空，说明它没有进入实际规划流程。下一轮先从创建、编辑和 Inspector 中降低其存在感，并保留数据库字段以避免无必要迁移；如果完成一轮真实运营后仍没有使用场景，再评估删除。不要为了让字段非空而编造课程名称。

## 四、下一轮 Phase 04 优化 Plan

下一轮仍属于 Phase 04，不进入其他业务模块。

### Step 1：建立空白数据待确认状态

- 识别 6 个缺少数量规则的细致时间块；
- 主矩阵用 `?` 表示待确认；
- Inspector 显示“数量待确认”；
- 输出逐项确认清单；
- 用户确认后再保存真实数字；
- 总规划和纯月份范围不填虚构数量。

验收标准：

- 所有细致规划时间块都有数字规则或明确的 `?`；
- `?` 不被当作真实数量参与计算；
- 页面可以清楚区分“零”“一”和“未知”。

### Step 2：重做年度矩阵视觉

总规划：

- 重新建立统一列网格，让科目、周期和 1—12 月表头与内容严格对齐；
- “发帖周期”“推广周期”在自己的固定列中水平和垂直居中；
- 总规划使用更克制的只读视觉，不与细致规划争夺层级；
- 检查分区切换和横向滚动时表头、内容是否仍处于同一列线。

细致规划：

- 统一“规划分区 / SOP / 规划项目 / 1—12 月”的列宽、基线和行高；
- 修正当前表头拥挤、文字断裂和粘性列层级混乱；
- SOP 列只承担箭头入口；
- 规划项目列承担名称和 V0/V1 状态；
- 月份条幅只承担时间范围和数量规则；
- 在 1280、1440 和常见笔记本宽度分别验收，不只检查单一屏幕。

### Step 3：重做 Inspector

- 按“规划身份 → 当前状态 → 时间块 → SOP → 版本”重新组织信息；
- 使用与内容发布控制台一致的间距、字号、层级和操作区；
- 不在顶部重复数据库字段；
- 数量待确认、停用和推广汇总必须有文字说明；
- 编辑入口固定且明确；
- 桌面端保持右侧 Inspector，移动端使用全屏详情。

### Step 4：重做版本历史

- “查看全部版本”不再使用当前拥挤的展开列表；
- 使用独立历史视图或层级明确的 Sheet；
- 每个版本优先展示版本号、时间、修改者和调整说明；
- 差异按规划字段、时间块和链接分组；
- V0 明确标记“初始化基线”；
- 恢复动作放在版本详情中，并保留二次确认；
- 避免同时堆叠 Inspector、历史列表和快照详情。

### Step 5：清理冗余总规划数据

- 确认 7 条旧总规划不被任何页面或 API 引用；
- 保留当前自动汇总逻辑；
- 为 G5 是否需要建立细致规划来源留下开放问题；
- 通过新迁移删除旧总规划行及其子记录和 V0 快照；
- 迁移前后断言细致规划仍为 30 条、时间块和分类关联无意外变化。

### Step 6：回归验证

- 校验自动发帖周期和推广周期；
- 校验 30 条细致规划的学科—分类关系；
- 校验 V0 初始化状态；
- 校验新增和编辑规划；
- 校验版本历史与恢复；
- 校验 1280、1440、移动端和键盘操作；
- 执行 `pnpm test`、`pnpm db:check`、`pnpm check` 和 `pnpm build`。

## 五、何时从 Development 上线到 Production

目前不建议立即上线 production。应在以下条件全部满足后再安排：

1. 6 个细致规划数量空白已经由用户确认，或明确接受 `?` 作为正式待确认状态；
2. 总规划与细致规划的新版矩阵完成视觉验收；
3. Inspector 和版本历史完成交互验收；
4. 7 条冗余总规划记录完成安全清理，或明确决定暂时保留；
5. G5 是否属于当前年度规划获得结论；
6. 所有正式 SOP URL 已录入，或明确允许上线时为空；
7. development 中完成真实创建、编辑、V0→V1、历史查看和恢复测试；
8. 类型检查、测试、Drizzle 检查和构建全部通过；
9. production 上线前建立恢复点，并审核迁移 SQL；
10. 明确哪些 development 业务数据需要进入 production，并准备独立的数据迁移方案。

上线时应分别处理：

```text
代码部署
数据库结构迁移
经审核的业务数据迁移
生产环境变量
上线后冒烟测试
```

不能把 development 直接改名为 production，也不能认为执行 Drizzle migration 会自动复制 development 中手工录入的业务数据。

6. 用户何时正式宣布初始化 V0 结束、后续修改开始计为 V1。
