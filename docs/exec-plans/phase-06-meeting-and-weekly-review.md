# Phase 06 Plan — Meeting and Weekly Review

> 状态：06A—06C 主要实现已完成；待补齐可复盘的非推广真实数据后，再完成周度业务复盘最终验收。Monthly Review 口径仍待后续确认，不进入当前阶段命名与交付范围。

## 一、目标与原则

Phase 06 将非推广到期节点、推广日度事实、Annual Plan 和会议结论组织成可追踪的例会工作流。日度推广复盘继续作为原始事实入口；按周或按月的推广汇总、分析与结论只在例会总复盘中产生。

核心原则：

- **会议由日期区间定义**：周例会自由选择开始日与结束日，默认结束日为会议前一天；月例会默认使用完整自然月。
- **复盘对象保持分离**：非推广帖按 T+7、T+15 到期节点独立完成；推广按会议区间从日度事实聚合，不另建独立的推广阶段复盘事实。
- **未复盘自动结转**：跨周期或上次遗漏的内容自动进入下一次会议候选项。
- **自动数据、人工结论分离**：消耗、开口、留资、发布完成等从现有事实表汇总；判断、原因、策略和待办由人确认。
- **生成与定稿分离**：会议草稿可重新生成当前数据；会议定稿时保存指标、口径、手填值和结论快照，不被之后的事实更正静默改写。
- **先确认再联动**：Annual Plan 和排期的写入必须预览并确认，不直接由报告自动改动事实表。
- **历史按当时事实解释**：帖子分类、推广身份或分类默认规则后来发生变化时，旧排期、旧 Campaign、旧指标和旧复盘继续使用当时快照，不以当前配置回算历史。

## 二、实施顺序

### 06A：非推广帖 7 / 15 天复盘

先建立最小闭环。只纳入 `2026-07-01` 起已实发的非推广排期，4—6 月不进入正式待办或 cohort。每条排期以 `actual_publish_at` 为起点生成 T+7、T+15，严格完成前一节点后才开放下一节点。非推广复盘独立于会议；例会只引用已完成结果。

数据源除 `operations_content_version`、`operations_content_schedule` 和 Annual Plan 外，还需要接入内容表现事实。第一轮至少支持：

- 点击率；
- 3 秒阅读率；
- 直接录入点击率、3 秒阅读率百分比和数据截止时间；cohort 使用同节点样本的百分比进行均值、最大值和最小值比较。
- T+7 读取发布后第 1—7 天累计事实，T+15 读取第 1—15 天；迟到数据或历史更正不得悄悄改变已完成复盘，需通过明确的“刷新快照”操作留下修订记录。

同类基准按“相同学科 + 相同帖子分类 + 相同复盘节点”建立 cohort。页面至少展示样本数、均值、最大值和最小值，并将当前帖子与 cohort 对照；建议同时预留中位数，避免极端值让均值失真。样本不足时只展示已有样本及明确提示，不给出好坏判断。默认只纳入同一指标口径、已到达该节点且数据完整的排期；是否限制近 90 / 180 天或同一自然年，实施前用真实数据分布确认。

页面能力：

1. 自动列出全部到期但尚未完成的 T+7 / T+15 节点，历史遗漏持续保留并标记逾期。
2. 同一帖子严格按 T+7、T+15 顺序开放；即使两个节点都已到期，也必须依次补录。
3. 每篇内容展示学科、分类、内容版本、应发/实发、当前复盘节点、指标数据截止时间、点击率、3 秒阅读率和同类基准。
4. 基准对照可展开查看样本范围、样本数、均值、最大值、最小值，以及当前值在范围内的位置；不同节点不可混算。
5. 每个节点只记录一项复盘结论；保存即完成该节点并开放已经到期的下一节点。
6. 排期 Inspector 展示 7 / 15 天复盘轨道，区分未到期、待复盘、已完成和已结转；已完成节点保持低强调，仍需处理的节点保持醒目。
7. 每个“排期 + 节点”全局唯一；历史通过明确的编辑入口修订。例会只引用结果，不拥有或覆盖原始复盘事实。

#### 分类、用途与推广身份变更

“推广讲义帖”未来可能改为“对外讲义”且默认不再推广，这类变化必须能在平台内完成，但不直接改写历史记录。

不建议只给分类字典增加一个覆盖全局的 `version`，因为分类名称、默认推广用途和某一条排期的实际推广事实是三个不同概念。建议拆为：

1. **稳定分类身份**：分类保留不变的 ID；改显示名称时创建新的分类规则版本，不修改旧快照中的名称。
2. **分类规则版本**：记录显示名称、适用学科、是否可选、默认是否推广、生效时间和变更说明。新建帖子读取当前生效规则；旧内容版本和旧排期继续引用创建时快照。
3. **排期实际身份**：每条排期仍独立保存“推广 / 非推广”，分类的默认值只帮助新建，不强制覆盖单条排期。
4. **用途变更事件**：已发布帖子从推广改为非推广时，在平台执行“变更后续用途”，填写生效时间和原因。系统先预览影响，再结束或保留已有 Campaign，写入用途历史；已有推广日度事实和推广复盘永久保留，生效后的复盘按非推广规则进入尚未到期的 7 / 15 天节点。
5. **禁止静默搬家**：历史推广数据不能因当前身份变为非推广而进入非推广 cohort；同理，过去的非推广数据不能因未来默认推广而被重算。cohort 使用指标发生时的身份与分类快照。

平台需要提供一个受控的“分类与默认规则”管理入口，以及单条排期 Inspector 中的“变更后续用途”动作。两者都展示变更预览与影响数量；分类规则只影响生效后的新建内容，批量迁移既有内容必须作为独立操作再次确认。

06A 不建设复杂绩效评分、AI 自动判断或直接智能排期。

### 06A.1：控制台导航性能与共享 Sidebar 视觉优化

当前业务页通过普通 `<a href>` 完整跳转。每次点击 Sidebar 都会销毁当前文档，等待目标 Astro 页面完成服务端数据库查询和 HTML 生成后再重建 Sidebar，因此数据库稍慢时会表现为整页长时间加载。日度推广复盘还依次查询 Campaign、Stage、Daily Metric 和待推广排期，等待时间会叠加。优化只调整共享壳层、导航行为和查询路径，不重做右侧业务页面。

#### 导航与服务端性能

1. 在业务控制台共享壳层引入 Astro 客户端路由能力，Sidebar 跨路由持久化，页面切换时只替换右侧 Workspace。
2. 点击导航后立即更新高亮，并在右侧顶部提供轻量加载进度；即使服务端仍在查询，Sidebar 不消失、不闪白、不位移。
3. Sidebar 链接按 hover、键盘 focus 和移动端 touch start 受控预取；不得在首屏一次性预取全部业务页并并发触发全部数据库查询。
4. 日度推广复盘的 Campaign、Stage、Daily Metric 和待推广排期改为并行查询；历史数据按当前筛选日期下推数据库，不读取全部历史后在页面内过滤。
5. “最新生命周期”只查询仍处于测试或放量中的 Campaign；已结束和已淘汰活动只进入历史视图。
6. 检查 Campaign 状态、Stage、`metric_date` 和常用范围筛选索引；稳定分类字典和低频设置数据只在证明有收益后增加短时服务端缓存。
7. 为业务页响应增加 `Server-Timing`，分别记录数据库查询和页面生成耗时，以真实数据决定后续优化，不用主观加载感替代测量。

性能验收目标：

- 点击后导航高亮在 50ms 内出现；
- Sidebar 在跨页过程中不销毁、不消失，布局位移为 0；
- 已预取页面目标 300ms 内出现右侧内容，未预取页面目标 800ms 内出现；
- 日度推广复盘数据库查询目标低于 300ms；若 development 数据库网络本身超过目标，必须通过 `Server-Timing` 明确区分网络与应用耗时。

2. 当前“总、排、日、非、会”汉字方块替换为项目内语义 SVG 线性图标，统一 `18px`，不再为图标单独增加方形底色。
3. 激活态使用完整的淡蓝灰圆角选择面、蓝色语义图标和加深文字，不叠加蓝色方块、状态线或外阴影；按压只提供轻微缩放和颜色反馈。

### 06B：周例会

周例会是推广区间数据的唯一汇总与结论入口，不再建设独立的“推广阶段复盘”页面。会议草稿先选择时间范围；例如周一开会，默认统计至上一个自然日，开始日由用户确认。

#### 06B.1 会议区间与生成

1. 创建会议时选择“周例会”、会议时间、数据开始日和结束日。
2. 新建时默认结束日为会议日前一天；不强制固定周一或七天，但必须明示实际统计天数。
3. 系统纳入与区间有交集的推广 Campaign，只聚合该区间内的 Daily Metric。
4. 草稿可重新生成；会议定稿后保存数据与口径快照。
5. 日度事实缺失时明确标出缺失日期，不把缺数据的部分包装成完整周数据。

#### 06B.2 推广区间复盘

“推广区间复盘”是周例会内的内容区，不是独立导航或独立业务模块。

- 自动聚合：总消耗、平台/实际开口、平台/实际留资、实际开口成本和实际留资成本。
- 人工填写：当前无法从日度事实可靠推导的周汇总点击率等平台指标，同时保存数据截止时间与口径说明。
- 测试/放量默认分开：按 Daily Metric 的 Stage 快照分别聚合，同时提供整个会议区间的合计。
- 相邻阶段可合并展示：测试紧接放量时，用户可切换“分开 / 合并”视图；合并只改变会议展示和结论组织，不改写原始 Stage 或 Daily Metric。
- 一个区间内可同时查看单帖、测试合计、放量合计和全部推广合计。

#### 06B.3 环比

环比必须优先保证对象和口径可比，不因为“上周有数”就强行给出百分比。

1. 优先对比同一帖子身份、同一内容版本在上一个已定稿周例会的区间数据。
2. 如当前是改帖版本，可将直接上源版本作为“版本对比”，必须标明不是同版本环比。
3. 没有同帖或直接版本数据时，只提供同学科、同分类参考，不命名为环比。
4. 对比消耗、实际开口、实际留资及两项成本；手填点击率只在口径一致时对比。
5. 统计天数不同或数据不完整时，页面必须提示；总量与日均值分开展示。

#### 06B.4 周例会内容

一次周例会按以下顺序组织：

1. 区间总览与数据完整性；
2. 推广区间复盘；
3. 本周到期或遗留的非推广 T+7 / T+15 结果引用；
4. Annual Plan 与排期执行对齐；
5. 核心结论、待拍板事项与下一周动作。

### 06C：例会总览与事项跟进

“例会总览”是例会总复盘的默认首页，统一管理周例会和月例会：

1. 按会议时间倒序展示会议类型、数据范围、会议状态、数据完整性和核心结论。
2. 支持创建草稿、继续编辑、定稿和查看历史；会议定稿后不静默重算。
3. 会议详情保留开会时间、数据范围、参与复盘项、自动数据快照、人工指标、核心结论和行动项。
4. 核心结论提供独立的发布/归档区，作为会议记录中最易查看和复用的部分。
5. 待拍板、待验证和待解决事项保存负责人标识、目标日期、状态和进展，未完成项可带入下次会议。
6. 已定稿会议提供适合浏览器打印的页面；第一轮不引入独立 PDF 服务。

### 06D：月例会

月例会在周例会的指标口径和会议快照稳定后实施，默认使用完整自然月：

- 从日度推广事实汇总当月消耗、开口、留资和成本，不重复录入；
- 汇总当月已定稿周例会的核心结论、未完成事项和重要变化；
- 按学科、帖子分类和整体三个层级展示推广表现；
- 支持私域新增人数等无法从当前系统生成的月度人工事实，必须保存口径与数据截止时间；
- 记录本月主要动作、月度核心结论与下月整体策略；
- 从 Annual Plan 读取下月任务作为对齐信息；排期变更和自动写入不在本轮默认范围内，需另行确认规则。

```text
review_meeting

meeting_promotion_snapshot
  会议、Campaign、帖子与版本快照、区间、测试/放量分组、自动汇总、人工指标、口径和环比基线

non_promotion_review

non_promotion_review_snapshot

category_policy_version
  稳定分类 ID、显示名称、适用学科、是否可选、默认推广身份、生效时间和变更说明
```

## 四、交互与导航

内容发布控制台建议逐步形成：

```text
日度推广复盘
非推广复盘
例会总复盘
├─ 例会总览
├─ 周例会
│  └─ 推广区间复盘
└─ 月例会（06D）
```

独立事实入口统一命名为“日度推广复盘”。周例会内的聚合内容命名为“推广区间复盘”；不使用“阶段推广复盘（7—15 天）”，因为会议区间由用户选择，不一定等于完整测试或放量 Stage。

## 五、验收节点

### 06A 完成条件

- 正式数据能正确识别到期的 T+7 / T+15 非推广节点和历史结转项；
- 同一排期能依次完成两个节点，同一节点不重复生成；
- 点击率与 3 秒阅读率按确认口径直接录入百分比，并保留数据截止时间；
- 相同学科、分类和节点的 cohort 能正确给出样本数、均值、最大值和最小值，且不混入不同口径或不同历史身份；
- 排期页面能辨识三个节点各自的未到期、待复盘、已完成和继续跟进状态；
- 在平台内修改分类默认规则或单条帖子的后续推广用途后，旧 Campaign、旧指标和旧复盘保持可查，未来待办按新身份生成；
- 非推广结论、指标快照、分类规则版本与用途变更均可追溯。

### 06A.1 完成条件

- Sidebar 跨页面切换持续存在，只替换右侧 Workspace，加载中有明确但克制的反馈；
- 受控预取不会在页面打开时并发请求所有业务页；
- 日度推广复盘的独立数据查询并行执行，历史范围筛选在数据库完成；
- `Server-Timing` 能区分数据库、页面生成和总响应耗时；
- 六个业务页面使用同一套 Quiet Operations Sidebar，跨页宽度、垂直位置、导航密度和激活态不跳动；
- Sidebar 共享组件继续隔离页面级盒模型、字体和行高，业务页面不存在独立侧栏结构或样式。

### 06B 完成条件

- 可选择周例会日期范围，默认数据截止会议前一天；
- 推广自动聚合值可从 Daily Metric 复算，缺失日期明确可见；
- 测试与放量默认分开，相邻时可合并展示且不改写原始事实；
- 周汇总点击率等人工指标保存口径与数据截止时间；
- 同帖同版本环比、直接上源版本对比和同类参考不被混用；
- 会议定稿后保存完整数据快照。

### 06C 完成条件

- 例会总览能统一查看周例会、月例会、会议时间、数据范围和状态；
- 会议核心结论可单独查看和归档；
- 历史会议可查看并能通过浏览器打印；
- 未完成事项能带入后续会议并保留进展。

### 06D 完成条件

- 月例会默认使用完整自然月，并能汇总当月日度事实与已定稿周会结论；
- 月度人工事实保存口径和数据截止时间；
- 月度核心结论、下月策略与 Annual Plan 对齐可查看；
- 未经另行确认不自动写入真实排期。

## 六、进入实施前需要确认

1. 点击率的原始分子 / 分母分别是什么，3 秒阅读率的分母使用曝光、打开还是其他平台口径；数据通过人工录入、文件导入还是现有来源取得。
2. cohort 默认时间窗使用近 90 天、近 180 天、同一自然年还是全部历史；低于多少个完整样本时只展示数据、不形成比较结论。
3. 已经开始推广的帖子切换为非推广时，开放 Campaign 是立即结束、指定日期结束，还是仅停止未来推广但保留开放状态；该选择会影响用途变更流程。
4. “推广讲义帖 → 对外讲义”是同一稳定分类的改名与默认用途变化，还是两个需同时保留的独立分类；若两者未来会并存，应创建新分类而不是改名。
5. 周例会默认开始日是上次会议区间的次日，还是按自然周推导；当两次会议区间重叠或留空时是仅提示还是禁止定稿。
6. 周汇总点击率的平台口径、录入粒度（按帖子或整场会议）与数据截止时间。
7. “测试紧接放量”是否只允许日期无缝时合并展示，以及合并后是否允许填写一条共同结论。
8. 环比的默认基线是上一个已定稿周例会，还是上一个等长日期区间；无等长数据时是否仅展示日均值。
9. 待办事项是否需要明确负责人账号；当前 Basic Auth 用户名尚不是正式人员与权限系统。
10. 浏览器打印是否足够；Annual Plan 对齐在本轮只读，如需从会议写入 Schedule，需另行确认冲突、预览和撤销规则。
