# Phase 05 Plan — Daily Promotion Review

> 状态：首轮已实现，等待真实推广数据验收。Phase 05 当前只处理推广帖的日度数据、测试/放量状态和生命周期日历。

## 一、目标

建立一套可以每天完成以下工作的推广复盘页面：

- 看到当前正在测试或放量的帖子；
- 按 T+1 规则填写每篇推广帖前一天的数据；
- 自动计算当天实际开口成本和实际留资成本；
- 填写数据后确认下一自然日继续、转阶段或结束；
- 在推广日历中看清每篇帖子的测试、放量和结束节点；
- 从日历进入当天数据，从帖子进入单帖 Inspector。

排期和内容版本继续提供帖子身份、发布时间、项目文档、学科与分类。Phase 05 只新增推广活动、阶段和日度数据。

## 二、启动与每日闭环

### 1. 测试期自动启动

排期满足以下条件时，系统立即启动推广测试：

1. 排期的 `is_promoted` 为 `true`；
2. 排期已经填写实发日期。

系统在同一个事务中：

- 将排期当前推广状态更新为“推广测试中”；
- 创建推广活动；
- 创建从实发日期开始的测试阶段；
- 允许实发日期当天产生第一条推广日度数据。

如果推广帖尚未填写实发日期，则保持待发布或待推广，不进入 Daily Promotion Review 的日度待填和生命周期日历。

排期新增独立布尔字段 `is_promoted`：

```text
false：非推广帖
true：推广帖
```

`is_promoted` 负责稳定判断一条排期是否属于推广，`promotion_status` 负责表达待推广、测试、放量、结束或淘汰。推广结束或淘汰后，`is_promoted` 仍保持 `true`，避免历史推广帖被误判为非推广。

### 2. T+1 填报

员工在下一自然日填写前一天数据：

```text
7 月 30 日：推广实际发生
7 月 31 日：填写 7 月 30 日数据并完成每日复盘
```

今日待填默认定位到昨天，只催促昨天仍处于测试或放量阶段、且尚未完成复盘的推广帖。历史漏填通过补录入口处理，不混入默认今日流程。

### 3. 每日复盘决定

一条日度数据只有在“指标已填写 + 下一步已选择”后才算完成复盘。

测试期可选：

- **测试继续**；
- **测试淘汰**；
- **测试接放量**。

放量期可选：

- **放量继续**；
- **放量淘汰**；
- **推广周期结束**。

“继续”也是需要保存的明确业务决定，不只是关闭页面。

### 4. 决定的生效日期

每日复盘决定默认从被复盘日期的下一自然日生效：

```text
7 月 31 日填写 7 月 30 日数据
7 月 30 日阶段快照：保持当天真实阶段
7 月 31 日阶段：由本次复盘选择决定
```


| 7 月 30 日阶段 | 复盘选择   | 7 月 31 日状态 |
| ---------- | ------ | ---------- |
| 测试中        | 测试继续   | 测试中        |
| 测试中        | 测试淘汰   | 测试淘汰       |
| 测试中        | 测试接放量  | 放量中        |
| 放量中        | 放量继续   | 放量中        |
| 放量中        | 放量淘汰   | 放量淘汰       |
| 放量中        | 推广周期结束 | 推广周期已结束    |


为了避免迟填造成时间线冲突，同一推广活动应按日期顺序完成复盘。存在更早的未完成日期时，系统先引导补齐最早一天，再处理后续日期。

### 5. 修改实发日期

推广活动创建后，如果员工修改该排期的实发日期，系统执行破坏性重置：

1. 明确显示将被删除的推广活动、阶段和日度记录数量；
2. 要求员工二次确认；
3. 在同一个事务中删除该排期关联的全部推广日度数据、阶段和推广活动；
4. 更新实发日期；
5. 按新的实发日期重新创建测试期推广活动。

取消确认则不修改实发日期。确认后旧推广日历和日度数据不在应用内保留，员工需要按照新日期重新填写。

## 三、日度数据

### 1. 每天手工填写


| 字段     | 含义                                    | 候选类型         |
| ------ | ------------------------------------- | ------------ |
| 消耗     | 当天推广消耗金额                              | 非负金额         |
| 点击率    | 当天平台点击率，界面直接填写百分数，例如 `12.5%` 填 `12.5` | `0—100` 的百分数 |
| 平台开口人数 | 平台记录的开口人数                             | 非负整数         |
| 实际开口人数 | 员工核对后记录的真实开口人数                        | 非负整数         |
| 平台留资人数 | 平台记录的留资人数                             | 非负整数         |
| 实际留资人数 | 员工核对后记录的真实留资人数                        | 非负整数         |


### 2. 系统自动计算


| 字段     | 确认公式            |
| ------ | --------------- |
| 实际开口成本 | 当天消耗 ÷ 当天实际开口人数 |
| 实际留资成本 | 当天消耗 ÷ 当天实际留资人数 |


两项实际成本不作为手工输入，也不重复保存为独立事实；页面根据当日输入实时计算。对应分母为 `0` 或尚未填写时显示 `—`，不显示无穷大或虚假的 `0`。

### 3. 暂存的后续口径

如果后续进入周度复盘，一周点击率按照用户确认的算术平均计算：

```text
周点击率 = 有效日点击率之和 ÷ 有效天数
```

本阶段不实现周度、月度或年度页面。

## 四、推广状态

当前推广日度复盘只处理以下状态：


| 状态      | 日度行为                |
| ------- | ------------------- |
| 推广测试中   | 每天进入待填，日历显示测试段      |
| 推广放量中   | 每天进入待填，日历显示放量段      |
| 推广周期已结束 | 停止生成后续待填，保留历史       |
| 测试淘汰    | 停止生成后续待填，日历显示测试淘汰节点 |
| 放量淘汰    | 停止生成后续待填，日历显示放量淘汰节点 |


### 1. 测试期每日决定

- **测试继续**：下一自然日继续测试；
- **测试接放量**：结束测试段，下一自然日开始放量；
- **测试淘汰**：结束测试段，下一自然日起停止生成推广日度待填。

### 2. 放量期每日决定

- **放量继续**：下一自然日继续放量；
- **推广周期结束**：结束放量段，下一自然日起停止生成推广日度待填；
- **放量淘汰**：结束放量段，下一自然日起停止生成推广日度待填。

状态转换不能修改此前已经保存的日度状态快照。

## 五、页面结构

```text
Daily Promotion Review
├── 今日待填
├── 推广日历
├── 日度数据表
└── 推广 Inspector
```

### 1. 今日待填

默认展示昨天处于推广测试中或推广放量中、且尚未完成日度复盘的帖子。

每行展示：

- 首图占位、帖子名称和版本；
- 学科与帖子分类；
- 当前测试或放量状态；
- 当天是否已经填写；
- 填写/编辑数据；
- 本次复盘决定。

### 2. 推广日历

推广日历使用真实自然日期作为横轴，每篇推广帖占一条生命周期轨道：

```text
日期       7/01        7/07        7/14        7/21
今天游标                              │
帖子 A     [ 测试阶段 ] [──── 放量阶段 ────]  ● 正常结束
帖子 B              [ 测试阶段 ]      │
帖子 C       [ 测试阶段 ]  × 测试淘汰
```

日历需要表达：

- 测试开始与结束；
- 测试接放量转换节点；
- 放量开始与结束；
- 正常结束、测试淘汰和放量淘汰；
- 今天或所选日期的时间游标；
- 哪些日期已经填写日度数据。

横向长度按真实天数绘制。长生命周期允许横向滚动，帖子身份列保持冻结。

点击某一天进入该帖当天的数据；点击帖子身份打开 Inspector。

### 3. 日度数据表

日度数据表是主要填写界面：

- 按日期查看当天全部推广帖；
- 表格行内填写 6 项日度数据；
- 实时显示 4 项自动成本；
- 支持保存单行；
- 是否需要批量保存，在完成单行流程后再判断；
- 清楚区分未填写、数值为 `0` 和不适用。
- 指标与复盘决定全部完成后，才把该日标记为“已复盘”。

### 4. 推广 Inspector

Inspector 展示单篇推广帖：

```text
帖子与排期身份
→ 当前推广状态
→ 测试 / 放量生命周期
→ 当前所选日期数据
→ 日度数据入口
```

本阶段 Inspector 不增加周度、月度或年度汇总。

## 六、候选数据结构

### 1. 推广活动

```text
operations_promotion_campaign
- id
- schedule_id
- started_on
- ended_on
- current_stage
- current_status
- created_at
- updated_at
```

推广活动关联具体排期。未来同一排期再次推广时，可以建立新活动，不覆盖第一轮历史。

排期表同步新增：

```text
operations_content_schedule
- is_promoted boolean not null default false
```

状态一致性：

- `is_promoted = false` 时，推广状态必须为非推广；
- `is_promoted = true` 且未实发时，可以处于待推广；
- `is_promoted = true` 且首次填写实发日期时，自动进入推广测试中；
- 推广周期结束或淘汰后，`is_promoted` 仍为 `true`。

### 2. 推广阶段

```text
operations_promotion_stage
- id
- campaign_id
- stage_type       testing / scaling
- started_on
- ended_on
- outcome
- created_at
- updated_at
```

### 3. 推广日度数据

```text
operations_promotion_daily_metric
- id
- campaign_id
- metric_date
- stage_type_snapshot
- spend
- click_rate
- platform_open_count
- actual_open_count
- platform_lead_count
- actual_lead_count
- review_decision
- reviewed_at
- note
- created_at
- updated_at
```

数据库规则：

- `campaign_id + metric_date` 唯一；
- 金额和比例使用精确 decimal，不使用浮点数；
- 点击率按界面百分数录入并限制在 `0—100`；
- 人数使用非负整数；
- 两项实际成本分别从消耗与实际开口、实际留资人数计算；
- 修改当天数据更新原记录，不生成重复行；
- 历史 `stage_type_snapshot` 不随当前状态变化。
- `review_decision` 必须属于当前阶段允许的三种选择；
- 保存最终复盘决定时，在事务中更新下一自然日状态和阶段边界；
- 存在更早未完成日度复盘时，不允许跳过日期直接确认后续决定。

## 七、实施步骤

### Step 1：确认字段口径

当前已经确认：

- 推广帖填写实发日期后立即进入测试期；
- 排期使用独立的 `is_promoted` 布尔字段判断是否属于推广帖；
- 第一条日度数据归属于实发日期当天；
- 默认在下一自然日填写前一天数据；
- 每日指标填写后必须选择继续、转阶段或结束；
- 决定从被复盘日期的下一自然日生效；
- 同一推广活动按日期顺序完成复盘。
- 点击率在界面按百分数填写；
- 同时计算平台/实际开口成本和平台/实际留资成本；
- 修改实发日期会删除关联的全部推广活动、阶段和日度数据，再从新日期重新开始。

验收结果：字段、公式、启动条件、T+1 填报和实发日期重置规则全部明确。

### Step 2：建立数据库结构

- 新增推广活动、阶段和日度数据 Drizzle schema；
- 为排期新增 `is_promoted` 并建立状态一致性校验；
- 生成并审查迁移；
- 建立唯一约束、非负校验和索引；
- 建立状态转换事务；
- 建立按日期顺序完成复盘的约束；
- 为现有测试中和放量中的排期准备安全映射规则。

验收结果：数据库可以保存一篇推广帖连续多天的数据，并正确保留阶段历史。

### Step 3：实现日度 API 与校验

- 实现读取指定日期日度数据；
- 实现新增和编辑当天数据；
- 实现百分比校验与两项实际成本计算；
- 实现六种每日复盘决定；
- 实现下一自然日状态生效与日期顺序校验；
- 实现修改实发日期前的影响统计、二次确认和事务重置；
- 增加数据库与 API 测试。

验收结果：不依赖页面也能完整跑通日度保存和状态转换。

### Step 4：实现日度数据表

- 默认打开昨天的待复盘列表，并支持历史补录；
- 实现 6 项日度输入；
- 实时显示 4 项自动成本；
- 根据当天阶段显示对应的三个复盘选项；
- 实现保存反馈、错误提示和重复编辑；
- 先完成单行保存，再决定是否需要批量保存。

验收结果：员工可以每天完成真实数据填写。

### Step 5：实现推广日历

- 建立真实日期轴和冻结帖子身份列；
- 绘制测试段、放量段和结束节点；
- 实现今天/所选日期游标；
- 标记已填写和待填写日期；
- 从日期进入日度数据，从帖子进入 Inspector；
- 验证长生命周期横向滚动。

验收结果：可以直接看出每篇推广帖当前处于哪个阶段，以及完整生命周期如何变化。

### Step 6：实现推广 Inspector

- 展示帖子、版本和排期身份；
- 展示单帖测试/放量生命周期；
- 展示当前所选日期的 6 项数据和 4 项成本；
- 提供返回日历和日度数据表的入口。

验收结果：从排期、日历或日表进入同一篇帖子时，身份、状态和当天数据一致。

### Step 7：回归验证

- 验证连续多日日度数据和同日唯一约束；
- 验证实发后自动进入测试、T+1 待办和按日期顺序复盘；
- 验证 `0`、未填写、非法负数和 decimal 精度；
- 验证点击率百分数边界和两项实际成本分母；
- 验证测试接放量、测试淘汰、正常结束和放量淘汰；
- 验证修改实发日期前的影响提示和确认后的完整事务重置；
- 验证历史阶段快照不被当前状态覆盖；
- 验证日历比例、时间游标和填写状态；
- 验证桌面端、移动端、键盘操作和数据库异常；
- 执行测试、Drizzle 检查、Astro 检查和构建。

验收完成后，用户可以提供一批真实或脱敏的推广日度数据，再制定一次性安全导入方案。导入不是当前页面实现的前置条件。
